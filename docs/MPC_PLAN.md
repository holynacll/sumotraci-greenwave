## 1. Context

### 1.1 What this codebase does

The repo simulates emergency vehicle (EV, ambulance) dispatch in a Manhattan-style
grid network using SUMO + TraCI. The simulation generates accidents, dispatches
EVs after a delay, and routes them through traffic to the accident scene.

Two algorithms are currently selectable via `--algorithm`:
- `default` — SUMO's stock traffic-light behavior. EV gets no preemption.
- `proposto` — the existing **EDF + Green Wave** approach: when an EV is within
  `VEHICLE_DISTANCE_TO_TLS` (300m) of a TLS, the algorithm forces a green
  phase for the EV's lane on that TLS. Concurrent EV requests at the same TLS
  are arbitrated by Earliest Deadline First.

Implementation lives at:
- `src/sumotraci/managers/traffic/manager.py` — orchestration
- `src/sumotraci/managers/traffic/green_wave.py` — phase FSM (initial → in_progress → final → return)
- `src/sumotraci/managers/traffic/edf.py` — preemption arbitration

### 1.2 Why MPC

The current Green Wave is **reactive and local**: each TLS is preempted in
isolation, only when the EV is already nearby. This leaves two gaps:

1. **No coordination across TLS** — there's no anticipation of the EV's
   arrival at downstream TLS. If the EV exits TLS-A and enters a queued
   approach to TLS-B, that queue could have been pre-drained.
2. **No explicit trade-off model** — the cost imposed on cross-traffic
   by holding green is not represented anywhere. Severity/deadline only
   affect arbitration, not the duration or timing of preemption.

MPC addresses both: it optimizes a sequence of phase decisions across the
EV's downstream TLS, with an objective that explicitly trades EV delay
against queue growth on competing approaches.

### 1.3 Scenario summary

- Grid `5 × 5` (25 TLS, 40 edges of 300 m each, 3 lanes per direction)
- ~4800 background vehicles (random trips, fixed seed)
- Up to 4 simultaneous accidents; EVs dispatched with 120s delay
- Severity → "golden time" deadline: CRITICAL=700s, HIGH=850s, MEDIUM=1000s, LOW=1300s
- Simulation horizon: 900s (default)

### 1.4 Output metrics

Generated by SUMO and post-processed:
- `data/tripinfo.csv` — per-vehicle travel time (the EV travel time we want to minimize)
- `data/lanedata.csv` — per-lane throughput/occupancy (the proxy for "delay to others")
- `data/summary.xml` — global stats per step

The Pareto plot we want is **EV travel time** (y) vs **mean delay of non-EV vehicles** (x), parameterized by α (weight in MPC objective).

## 2. Glossary

Read this if any term in later sections is unfamiliar.

| Term | Definition |
|------|------------|
| **MPC** | Model Predictive Control. At each control step, solve an optimization problem over a finite future horizon using a model of system dynamics, apply only the first action, then re-solve at the next step with updated state. |
| **Rolling horizon** | The "re-solve every step" pattern of MPC. Each solve looks N steps ahead but only the immediate action is committed. |
| **LP** | Linear Program. Optimization with linear objective + linear equality/inequality constraints + continuous variables. Solvable in polynomial time. |
| **MILP** | Mixed-Integer Linear Program. Like LP but some variables are integer/binary. NP-hard in general; modern solvers handle moderate sizes well. |
| **QP** | Quadratic Program. LP with a quadratic objective. |
| **Solver** | The numerical engine that finds the optimum. We use **CBC** (COIN-OR Branch-and-Cut), which is open-source and bundled with PuLP. |
| **PuLP** | Python library for *modeling* LP/MILP problems. You write variables, constraints, objective in Python; PuLP forwards to a solver (CBC by default). |
| **Store-and-Forward (S&F)** | A traffic model where each lane's queue evolves linearly: `q(t+1) = q(t) + arrivals - saturation_flow × green_fraction`. Used in classical signal control papers (Aboudolas, Diakaki). |
| **CTM** | Cell Transmission Model. Models lanes as cells; captures backward propagation of congestion. More accurate than S&F but introduces non-linearities. **Out of scope here.** |
| **Saturation flow** | Maximum vehicles per second a lane can discharge while green. Typically 0.5–0.6 veh/s/lane. |
| **TLS** | Traffic Light Signal — a single intersection's controller. |
| **Phase** | A configuration of red/yellow/green across all approaches of a TLS. A typical 4-arm intersection has 2 main phases (NS-green, EW-green) plus yellow transitions. |
| **Cycle** | Sum of all phases at a TLS. Default in our scenario: ~60s. |
| **Green fraction (split)** | Fraction of the cycle allocated to a given phase. The decision variable in our LP. |
| **EDF** | Earliest Deadline First — scheduling policy that preempts in favor of the task with the earliest deadline. |
| **Safety shield** | A rule-based override on top of an optimizer/learner that enforces hard safety constraints (e.g., minimum green, mandatory yellow, force-green for nearby EV). |

## 3. Design Decisions (Locked)

These are committed. Each has an evolution path documented in §12.

### 3.1 Solver: PuLP + CBC

**Why**: free, ships in pip wheel, no license, mature, sufficient for LPs of
this size (≤ ~1000 vars). PuLP's modeling syntax is readable, which matters
for a research codebase that others will inspect.

**Add to dependencies**: `pulp >= 2.7.0` (CBC binary is bundled).

### 3.2 Traffic model: Store-and-Forward

**Why**: linear → keeps the optimization an LP. The classical literature
(Diakaki 2002, Aboudolas 2009) shows S&F is sufficient for signal-split
optimization in dense urban grids. We do not need queue spillback modeling
to demonstrate the contribution.

**Equation** (per lane *l*, per discrete time step *t* of duration *dt*):

```
q_l(t+1) = q_l(t) + arr_l(t) · dt − sat_l · x_p(l)(t) · dt
q_l(t)  ≥ 0   (queues cannot go negative)
```

Where:
- `q_l(t)`: queue length on lane *l* at step *t* (vehicles)
- `arr_l(t)`: arrival rate on lane *l* (vehicles/sec) — estimated from upstream demand or current TraCI measurements
- `sat_l`: saturation flow (vehicles/sec when green) — fixed constant, e.g. 0.55
- `x_p(l)(t)`: green fraction of phase `p(l)` (the phase serving lane *l*) at step *t* — **decision variable**
- `dt`: time step (use `dt = 1` second)

Negative-queue protection requires a slack variable in LP (see §8.3).

### 3.3 Decision variables: continuous green fractions

**Why**: yields a pure LP. Solving is sub-second. Easy to interpret: "TLS
J5 should give NS-phase 70% of the next cycle, EW-phase 30%."

**Variables**: for each TLS *i* in EV's route, each phase *p* of TLS *i*,
each step *t* in horizon:

```
x_{i,p,t} ∈ [0, 1]
```

Interpretation: fraction of step *t* allocated to phase *p* at TLS *i*.

Constraint: ∑ over phases p of x_{i,p,t} = 1 (one phase active per step).

### 3.4 Spatial scope: TLS on EV's remaining route only

**Why**: keeps problem size proportional to EV trip length, not to grid
size. For 5×5 grid, EV typically traverses 3–7 TLS → ~3–7 LPs to coordinate.

**Selection**: at each re-plan call, recompute the TLS list from
`vehicle_get_next_tls(ev_id)` filtered to the next K TLS within
`MPC_LOOKAHEAD_DISTANCE` (default 1500 m, ~5 TLS in our grid).

### 3.5 Re-plan cadence: every 5 simulated seconds

**Why**: solver finishes well under 1 sec; re-planning every step (100ms)
wastes CPU and creates oscillations. 5s gives enough resolution to react
to EV motion (EV at 13.89 m/s travels ~70m per 5s window).

**Mechanism**: `MPCStrategy.improve(...)` checks `(sim_time - last_replan_time) >= 5`
before solving. Otherwise it just applies the cached plan's current step.

### 3.6 Horizon

- **Length**: 30 simulated seconds (= 30 steps when `dt=1s`).
- **Why**: long enough to cover EV's traversal of 2–3 TLS at typical speed; short enough that arrival-rate forecasts stay reliable.

### 6.4 Arrival rate estimation

Three options, in increasing complexity:

1. **Static** (Phase 1 default): use a precomputed average from a warmup run.
   Save once, reuse. Simplest.
2. **Sliding window**: count vehicle entries on lane over last N seconds via
   repeated `lane_get_last_step_vehicle_number`. Update rate per re-plan.
3. **Upstream-aware**: query queue on upstream edge + travel time to estimate
   arrivals. More accurate but complex.

**Phase 1 implementation: option 2** (sliding window of 30s). Maintain a
deque per lane in `MPCStrategy._arrival_estimator`. Reset on `reset()`.

### 6.5 EV travel-time projection

For each TLS *i* in scope, predict `t_arr_i` = time when EV reaches stop
line of TLS *i*:

```
t_arr_i ≈ remaining_distance_to_tls_i / max(v_min, current_ev_speed)
```

where `v_min = 5.0 m/s` to avoid divide-by-zero when EV is stopped.
`remaining_distance_to_tls_i` comes from `vehicle_get_next_tls(ev_id)[i].distance`.

This projection is updated each re-plan; do not extrapolate further.

## 7. Phase 2 — Optimization Formulation

**Goal**: implement `_solve(obs)` returning a valid plan. Validate
mathematically (unit tests) before plugging into the simulation.

**Estimated effort**: ~1 week.

### 7.1 LP formulation

Given an `MPCObservation`, build an LP:

**Indices**:
- `i` ∈ TLS in scope
- `p` ∈ phases of TLS *i*
- `l` ∈ controlled lanes of TLS *i*
- `t` ∈ {0, 1, ..., H−1}, where H = `MPC_HORIZON_SECONDS / MPC_DT_SECONDS`

**Decision variables**:
- `x[i, p, t]` ∈ [0, 1] — green fraction for phase *p* of TLS *i* at step *t*
- `q[i, l, t]` ≥ 0 — queue on lane *l* of TLS *i* at step *t* (state, not free; constrained by dynamics)
- `d_ev[i]` ≥ 0 — EV "miss" slack at TLS *i* (objective penalty)

**Constraints**:

(a) **One phase active per step**:
```
∀ i, t:    Σ_p x[i, p, t] = 1
```

(b) **Queue dynamics (S&F)** — let `phase_serves(p, l)` be 1 if phase *p* gives green to lane *l*:
```
∀ i, l, t:   q[i, l, t+1] = q[i, l, t] + arr[i, l] · dt − sat[i, l] · dt · Σ_p phase_serves(p, l) · x[i, p, t]
∀ i, l, t:   q[i, l, t] ≥ 0
∀ i, l:      q[i, l, 0] = q_observed[i, l]
```

(c) **Min/max green** — over the cycle window (use sums; soft constraint version):
```
∀ i, p, cycle k:   g_min · cycle_length / dt ≤ Σ_{t in cycle k} x[i, p, t] ≤ g_max · cycle_length / dt
```
Skip this if it makes problem infeasible; use as soft penalty instead.

(d) **EV "request" at TLS i** — let `t_arr[i]` (rounded to nearest dt) be the predicted EV arrival step at TLS *i*, and `p_ev[i]` the phase that grants green to the EV's approach lane:
```
∀ i:   d_ev[i] ≥ 1 − x[i, p_ev[i], t_arr[i]]
∀ i:   d_ev[i] ≥ 0
```
(`d_ev[i] = 0` if EV finds full green; up to 1 if EV finds full red.)

**Objective**:
```
minimize    Σ_i d_ev[i]                          (EV penalty)
          + α · Σ_{i, l, t} q[i, l, t] · dt      (others' delay proxy)
```

`α` = `MPC_OBJECTIVE_ALPHA`.

### 7.2 PuLP skeleton

```python
import pulp

def _solve(self, obs: MPCObservation) -> MPCPlan:
    H = int(self.settings.MPC_HORIZON_SECONDS / self.settings.MPC_DT_SECONDS)
    dt = self.settings.MPC_DT_SECONDS
    alpha = self.settings.MPC_OBJECTIVE_ALPHA

    prob = pulp.LpProblem("mpc_signal_split", pulp.LpMinimize)

    # Variables
    x = {}     # x[(i, p, t)]
    q = {}     # q[(i, l, t)]
    d_ev = {}  # d_ev[i]

    for tls in obs.tls_in_scope:
        for p in tls.phases:
            for t in range(H):
                x[(tls.tls_id, p.phase_index, t)] = pulp.LpVariable(
                    f"x_{tls.tls_id}_{p.phase_index}_{t}", lowBound=0, upBound=1
                )
        for lane in tls.controlled_lanes:
            for t in range(H + 1):
                q[(tls.tls_id, lane.lane_id, t)] = pulp.LpVariable(
                    f"q_{tls.tls_id}_{lane.lane_id}_{t}", lowBound=0
                )
        d_ev[tls.tls_id] = pulp.LpVariable(f"d_ev_{tls.tls_id}", lowBound=0)

    # Constraints
    for tls in obs.tls_in_scope:
        # one phase active
        for t in range(H):
            prob += pulp.lpSum(x[(tls.tls_id, p.phase_index, t)] for p in tls.phases) == 1

        # initial queue
        for lane in tls.controlled_lanes:
            prob += q[(tls.tls_id, lane.lane_id, 0)] == lane.queue_length

        # queue dynamics
        for lane in tls.controlled_lanes:
            for t in range(H):
                green_share = pulp.lpSum(
                    x[(tls.tls_id, p.phase_index, t)]
                    for p in tls.phases if lane.lane_id in p.serves_lanes
                )
                prob += q[(tls.tls_id, lane.lane_id, t + 1)] == (
                    q[(tls.tls_id, lane.lane_id, t)]
                    + lane.arrival_rate * dt
                    - lane.saturation_flow * dt * green_share
                )

        # EV request
        ev_arrival = next(
            (a for a in obs.ev.tls_arrival_estimates if a[0] == tls.tls_id), None
        )
        if ev_arrival is not None:
            t_arr = min(int(round(ev_arrival[1] / dt)), H - 1)
            ev_lane = ev_arrival[2]
            ev_phase = next(
                p for p in tls.phases if ev_lane in p.serves_lanes
            )
            prob += d_ev[tls.tls_id] >= 1 - x[(tls.tls_id, ev_phase.phase_index, t_arr)]

    # Objective
    obj_ev = pulp.lpSum(d_ev[tls.tls_id] for tls in obs.tls_in_scope)
    obj_q = pulp.lpSum(
        q[(tls.tls_id, lane.lane_id, t)] * dt
        for tls in obs.tls_in_scope
        for lane in tls.controlled_lanes
        for t in range(H)
    )
    prob += obj_ev + alpha * obj_q

    solver = pulp.PULP_CBC_CMD(msg=False, timeLimit=2)
    prob.solve(solver)

    return self._extract_plan(prob, obs, x)
```

### 7.3 Plan extraction

```python
class MPCPlan(BaseModel):
    sim_time_at_solve: float
    horizon_steps: int
    dt: float
    actions_per_tls: Dict[str, List[Dict[int, float]]]
    # actions_per_tls[tls_id][step] = {phase_index: green_fraction}

def _extract_plan(self, prob, obs, x) -> MPCPlan:
    actions = {}
    for tls in obs.tls_in_scope:
        actions[tls.tls_id] = []
        for t in range(int(self.settings.MPC_HORIZON_SECONDS / self.settings.MPC_DT_SECONDS)):
            actions[tls.tls_id].append({
                p.phase_index: pulp.value(x[(tls.tls_id, p.phase_index, t)])
                for p in tls.phases
            })
    return MPCPlan(
        sim_time_at_solve=obs.sim_time,
        horizon_steps=int(self.settings.MPC_HORIZON_SECONDS / self.settings.MPC_DT_SECONDS),
        dt=self.settings.MPC_DT_SECONDS,
        actions_per_tls=actions,
    )
```

## 8. Phase 3 — Rolling Horizon Loop & Actuation

**Goal**: translate `MPCPlan` into TLS commands using the existing
`GreenWaveManager` for safe actuation, with a safety shield for nearby EVs.

**Estimated effort**: ~3–5 days.

### 8.1 Actuation strategy

The LP outputs **green fractions per step**, not a phase schedule. Two
interpretations are valid:

(a) **Per-step ratio**: at each sim-step *t*, the TLS spends fraction
`x[i, p, t]` of *dt* seconds in phase *p*. With `dt = 1s` this is too
fine — TraCI doesn't do sub-second phase switching cleanly.

(b) **Cycle-aggregated** (recommended): group H steps into K cycles
(default cycle = 60s). For each cycle, compute the average green fraction
per phase, then call `setPhase` / `setPhaseDuration` to enforce that split
for the upcoming cycle.

We use **(b)**. After each re-plan, set the next-cycle phase splits via
TraCI.

Concretely:
```python
def _apply_current_step(self, plan: MPCPlan, sim_time: float) -> None:
    elapsed = sim_time - plan.sim_time_at_solve
    step_index = int(elapsed / plan.dt)
    if step_index >= plan.horizon_steps:
        return  # plan exhausted; wait for re-plan

    for tls_id, action_list in plan.actions_per_tls.items():
        # Aggregate over the next cycle window starting at step_index
        cycle_window = action_list[step_index:step_index + int(60 / plan.dt)]
        if not cycle_window:
            continue

        avg_green_per_phase = self._average_green_fractions(cycle_window)
        self._set_phase_splits(tls_id, avg_green_per_phase)
```

`_set_phase_splits` uses `traci.trafficlight.setProgramLogic(...)` or the
simpler approach: set `setPhase(p)` and `setPhaseDuration(p, dur)` ahead
of cycle boundaries.

### 8.2 Safety shield (mandatory)

Wrap actuation with hard rules that override the LP:

1. **EV proximity override**: if any EV is within `MPC_SAFETY_SHIELD_DISTANCE_M`
   (default 50m) of TLS *i*, force the EV's phase to green immediately
   (using existing `GreenWaveManager.apply_green_wave` machinery).
2. **Min green guard**: never command a phase shorter than `MPC_MIN_GREEN`.
3. **Yellow obligatory**: any phase change inserts the configured yellow
   transition (handled by SUMO automatically when using `setProgramLogic`).
4. **Concurrent EV arbitration**: if two EVs converge on the same TLS,
   reuse `EDFManager` to decide which gets the priority. The MPC's plan
   for that TLS is overwritten with a safe-green for the higher-priority EV.

The shield reuses `EDFManager` and `GreenWaveManager` directly — do not
re-implement.

### 8.3 Numerical robustness

- LP infeasibility: if the LP returns infeasible, log a warning and skip
  this re-plan (keep the previous cached plan or fall back to no-op).
- Solver timeout: `timeLimit=2` in the solver. If exceeded, take the best
  feasible solution.
- Negative queue from arrival overshoot: `q ≥ 0` constraint already prevents.

## 11. Evolution Paths

When the time comes to upgrade a decision, here's how:

| Current | Next | Trigger |
|---------|------|---------|
| CBC solver | Gurobi (academic license) | Re-plan takes > 1s, blocking sim |
| Store-and-Forward | CTM | Need to model spillback explicitly for the paper |
| LP (continuous) | MILP (binary phase) | Need fine-grained phase scheduling within a cycle |
| Route-only TLS | Route + 1-ring neighbors | Experiments show MPC + larger scope improves more |
| 5s re-plan | 2s re-plan | Solver fast enough; need finer reactivity |
| Sliding-window arrival rate | Upstream-aware estimator | Static estimates yield poor predictions in dense traffic |

Each upgrade is a *swap*, not a rewrite — the architecture (Strategy +
LP-from-Observation) is designed to localize each change.
